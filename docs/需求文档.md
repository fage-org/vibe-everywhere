# Vibe Everywhere PRD

## 1. 背景与问题定义

个人开发者越来越多地把代码、依赖、开发工具链以及 AI coding agent 运行在远程主机上，例如 Linux 服务器、Mac mini 或基于 WSL 的开发环境。AI agent 在远程环境运行虽然更接近真实开发环境，但也带来了明显的问题：

- 用户一旦离开桌面端，就很难持续跟进远程 agent 的执行状态。
- 移动场景下，用户最需要的通常不是重度编辑代码，而是查看日志、追加消息、处理权限请求、确认 diff，以及中断或结束任务。
- 现有方案要么偏远程桌面，要么偏企业协作平台，要么默认桌面端优先，不够适合“个人开发者 + 手机接管远程 agent”这一高频场景。

因此，需要一款面向个人开发者的自建跨端产品，使用户可以在手机和桌面之间接力控制同一个远程 agent 会话，并用尽量低的部署成本获得稳定、可控的远程开发体验。

## 2. 产品定位

Vibe Everywhere 是一套面向个人开发者的自建跨端远程 agent 会话控制工具。

它的核心定位是：

- 远程 agent 会话控制台，而不是远程桌面
- 个人自建工具，而不是企业研发平台
- 跨端接力工具，而不是手机端 IDE
- 会话型产品，而不是一次性任务触发器

## 3. 目标用户

### 3.1 核心用户

- 个人开发者
- 独立开发者或单人维护远程开发环境的工程师
- 将 AI agent 运行在远程主机上的用户
- 需要在离开电脑后继续跟进和控制远程会话的用户

### 3.2 典型环境

- Linux 远程服务器
- macOS / Mac mini
- Windows 上的 WSL 环境

## 4. 产品目标

本产品首发版本的目标是：

1. 让用户可以直接在手机端创建远程 agent 会话
2. 让用户可以在手机和桌面之间无缝接力同一个长期会话
3. 让用户在移动端完成关键轻操作：查看日志、查看 diff、发送消息、处理权限、执行基础会话控制
4. 让用户以较低门槛完成服务器配置、主机接入和长期使用
5. 让权限体验尽量贴近 Claude Code，降低用户迁移成本

## 5. 非目标

以下内容明确不纳入首发版本：

- 企业能力：SSO、RBAC、多人审批、组织策略中心、企业合规审计
- 社交能力：公开分享、群聊、动态流、社区内容
- 远程桌面、VNC、RDP
- 手机端重度代码编辑
- Git clone / 拉代码 / 仓库托管
- `/plugins` 等依赖特殊子界面的命令支持
- 多用户首发体验
- 原生 Windows 非 WSL 的深度远程开发适配

## 6. 解决方案概述

产品采用“客户端 -> 服务端 -> 远程主机守护进程 -> agent”的固定拓扑：

- 客户端包括手机端和桌面端
- 服务端由用户自建，负责设备授权、连接管理、状态持久化、消息和事件转发
- 守护进程运行在远程主机上，负责管理一个或多个 agent
- 首发优先深度支持 Claude Code，其他 agent 通过 ACP 协议/适配层接入

该架构的目标是：

- 让客户端无需直接连接远程 agent
- 让主机和客户端都以更稳定的方式接入服务端
- 让会话状态、归档和通知更容易统一管理

## 7. 身份模型与设备模型

### 7.1 身份模型

首版采用单用户、无复杂账号体系的模式。

- 用户首次安装客户端后，配置服务器地址并连接到自建服务器
- 服务器为该用户生成设备授权体系
- 产品服务对象是“一个用户 + 多个设备”，而不是多人共享系统

### 7.2 设备模型

- 手机端和桌面端都属于用户自己的客户端设备
- 远程主机通过守护进程接入服务端
- 设备配对和主机配对均通过服务端统一完成授权与绑定

## 8. 首次安装与配对流程

### 8.1 客户端接入

1. 用户启动手机端或桌面端
2. 用户输入或配置服务器地址
3. 客户端连接服务器
4. 服务器生成当前客户端设备授权

### 8.2 远程主机接入

1. 用户在远程主机上首次运行守护进程，或执行 `connect` 命令
2. 守护进程连接配置好的服务器地址
3. 守护进程生成配对码，或生成二维码
4. 用户在手机端或桌面端扫码，或输入配对码完成绑定
5. 绑定成功后，远程主机出现在用户的主机列表中

## 9. 支持平台

### 9.1 客户端

- 手机端：必须支持
- 桌面端：必须支持，且为完整功能客户端

### 9.2 远程主机

- Linux
- macOS / Mac mini
- Windows：首版以 WSL 场景为主

## 10. agent 支持策略

### 10.1 首发支持

- P0：深度支持 Claude Code
- P1：通过 ACP 协议/适配层接入其他 agent

### 10.2 命令支持边界

首版支持常规对话命令，例如：

- `/init`

首版暂不支持会进入特殊子界面的命令，例如：

- `/plugins`

## 11. workspace 模型

workspace 以“远程主机上的一个目录”为单位。

### 11.1 支持能力

- 选择已有目录作为 workspace
- 创建新目录作为 workspace
- 如果目录不存在，可直接创建
- workspace 保存为后续快捷入口
- workspace 按主机分组展示
- workspace 支持收藏

### 11.2 不支持能力

- 不支持 Git clone
- 不支持仓库导入
- 不支持“最近使用目录”快捷入口

## 12. 会话模型

会话采用长期线程模型，而不是一次性任务模型。

### 12.1 会话原则

- 会话长期存在，可持续追加消息
- 会话支持在手机和桌面之间继续
- 用户可以主动关闭会话

### 12.2 关闭与归档

- 关闭后的会话进入归档状态
- 归档会话可查看，但不可继续运行
- 归档默认永久保留
- 用户可手动批量清理归档

## 13. MVP 功能需求

### 13.1 手机端功能

- 新建会话
- 选择主机和 workspace
- 发送消息给 agent
- 查看实时日志
- 查看 diff
- 按文件浏览变更
- 对变更做基础检索
- 只读浏览文件树
- 处理权限请求
- 执行基础会话控制动作
- 接收重要事件通知
- 配置通知类型或关闭通知

### 13.2 文件树浏览要求

- 文件树列出所有文件
- 文本文件支持只读浏览
- 非文本文件只展示元信息

### 13.3 桌面端功能

桌面端是完整功能客户端，首发需支持：

- 主机管理
- workspace 管理
- 会话列表与管理
- 会话归档与查看
- 查看日志
- 查看 diff
- 处理权限请求
- 给 agent 发送消息
- 执行会话控制动作
- 与手机端共享同一会话上下文

### 13.4 会话控制功能

首版必须支持：

- 暂停
- 终止
- 中断当前任务
- 重新运行
- 关闭并归档会话

## 14. 权限模型

权限体验以 Claude Code 为准。

### 14.1 首发支持的授权方式

- 单次允许
- 单次拒绝
- 本会话记住授权

### 14.2 首发重点覆盖的风险操作

- 文件写入
- 命令执行
- 网络访问

### 14.3 设计原则

- 保持安全
- 避免过度打断
- 尽量贴近 Claude Code 的使用心智

## 15. 通知模型

通知采用“只推送重要事件”的策略。

### 15.1 默认重要事件

- 权限请求
- 任务完成
- 任务失败
- 会话异常或中断

### 15.2 用户配置

- 用户可配置接收哪些事件类型
- 用户可完全关闭通知

## 16. 归档模型

### 16.1 归档内容

归档会话应支持查看以下内容：

- 消息历史
- 日志
- diff
- 文件树状态
- 基础元信息

### 16.2 归档规则

- 会话关闭后自动归档
- 归档只读
- 归档不可继续运行
- 默认永久保留
- 支持手动批量清理

## 17. 核心用户故事

1. 作为个人开发者，我希望在手机上直接创建远程 agent 会话，这样我不必先回到桌面端。
2. 作为远程开发者，我希望选择已有目录或创建新目录作为 workspace，这样我能快速开始任务。
3. 作为长期使用固定目录的用户，我希望 workspace 被保存并可收藏，这样我能快速再次进入。
4. 作为 Claude Code 用户，我希望产品优先支持它的核心工作流，这样我不用改变太多习惯。
5. 作为移动中的用户，我希望实时看到日志和关键事件，这样我能持续跟进 agent 状态。
6. 作为审阅变更的用户，我希望在手机上按文件查看 diff 并做基础检索，这样我能快速判断修改是否合理。
7. 作为需要更多上下文的用户，我希望能只读浏览整个文件树，这样我不只依赖 diff。
8. 作为处理资源文件的用户，我希望能看到所有文件，即使非文本文件只显示元信息。
9. 作为安全敏感用户，我希望高风险操作发生时收到权限请求，这样 agent 不会在我不知情时修改环境。
10. 作为高频使用者，我希望支持“本会话记住授权”，这样我不必为重复动作反复确认。
11. 作为跨设备用户，我希望在手机和桌面之间接力同一会话，这样上下文不会丢失。
12. 作为桌面用户，我希望桌面端能完整管理主机、workspace、会话和归档，这样我不需要依赖其他工具。
13. 作为只关心关键事件的用户，我希望通知只推重要信息，并且可配置，这样不会被无关消息打扰。
14. 作为长期用户，我希望归档默认永久保留，但也能手动批量清理，这样我可以自己管理历史记录。
15. 作为使用其他 agent 的用户，我希望未来可以通过 ACP 接入更多 agent，这样产品不会被锁定在单一生态。

## 18. 实现决策

- 首版为单用户系统，围绕“一个人、多设备”优化
- 采用“客户端 -> 服务端 -> 守护进程 -> agent”的固定架构
- 守护进程负责管理一个或多个 agent
- 首发优先适配 Claude Code 的会话模型和权限模型
- 其他 agent 先通过 ACP 协议/适配层接入
- 会话采用长期线程模型
- 会话关闭后进入归档，而不是直接删除
- workspace 采用“目录即工作区”模型
- 手机端聚焦控制与审阅，不承担重度编辑职责
- 桌面端是完整功能客户端，但整体产品不以 IDE 为目标
- 文件树支持全量列出，非文本文件只展示元信息
- 通知采用“重要事件推送 + 用户可配置”的策略
- Windows 首版以 WSL 为主

## 19. 测试决策

测试优先验证外部行为和用户结果，而不是内部实现细节。

### 19.1 重点测试对象

- 客户端配置服务器地址
- 主机配对流程
- workspace 创建与持久化
- 会话创建、接管、关闭、归档
- 权限请求、拒绝、会话记住授权
- 日志流与 diff 展示
- 文件树只读浏览
- 非文本文件元信息展示
- 通知触发与通知配置
- 跨设备继续同一会话

### 19.2 关键验收链路

1. 手机端配置服务器地址并成功接入服务端
2. 远程主机运行守护进程并生成配对码或二维码
3. 用户扫码或输码完成主机绑定
4. 手机端直接创建新会话
5. 移动端收到并处理权限请求
6. 桌面端成功继续同一会话
7. 会话关闭后进入归档且只可查看

## 20. 成功标准

首发版本达到成功的标志包括：

- 用户能在手机端独立完成主机接入和会话创建
- 用户能在手机和桌面之间无缝接力同一会话
- 用户能及时收到并处理权限请求
- 用户能在手机上看清代码变更并按文件浏览
- 用户能在桌面端完成主机、workspace、会话和归档管理
- 用户能在个人自建环境下低门槛部署并长期使用

## 21. 后续可扩展方向

以下方向可作为后续演进，但不进入首发版本：

- 多用户支持
- 更多 agent 的深度适配
- 更丰富的权限模式
- 更强的桌面端开发能力
- 更细粒度的通知策略
- 更复杂的归档管理和搜索能力
